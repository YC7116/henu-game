# 《河大寻迹：金明秘境》游戏开发总任务书 V1.0

## 一、项目介绍

我要开发一款名为《河大寻迹：金明秘境》的 2D 像素风校园探索 RPG 网页游戏。

项目用于河南大学与中源黑客松相关的校园黑客松比赛，建筑工程学院参与联合举办。

我是河南大学建筑工程学院软件工程（数智空间）专业的学生，希望作品既能体现河南大学校园文化，又能兼顾游戏趣味性、视觉效果、技术性和创新性。

**最重要的要求：必须分阶段开发，不能一次性完成整个项目。**

我希望每完成一个阶段，都能够亲自查看、试玩、提出修改意见，确认满意后再进入下一阶段。

目前部分故事内容、关卡机制和场景细节尚未确定，请不要擅自把这些内容全部定稿。

## 二、已确定的核心设计

### 1. 游戏名称

《河大寻迹：金明秘境》

### 2. 游戏类型

- 2D 像素风校园冒险 RPG
- 校园探索、NPC 互动、剧情引导和解谜闯关
- 单人游戏
- 优先适配电脑浏览器
- 使用 WASD 或方向键移动
- 通过 E 键或空格键与 NPC、建筑等交互

### 3. 游戏美术风格

参考《星露谷物语》的温馨像素 RPG 风格。

希望具备：
- 温暖、自然、明亮的校园氛围
- 精致、统一的像素美术
- 清晰的俯视或略带纵深感的 RPG 游戏视角
- 有细节的树木、草地、道路、水面和建筑
- 可爱的像素人物
- 精致但不过度复杂的游戏 UI
- 与校园环境协调的柔和配色

参考的是游戏的美术语言和交互体验，不直接复制《星露谷物语》的受版权保护素材。

不要做成扁平化网页地图、普通 PPT 风格，或只有简单几何块的最终画面。

如果第一阶段暂时使用占位素材，必须明确标注。

### 地图结构

已经确定采用：

**开场校园全景 + 分区域探索 + 独立任务场景。**

游戏进入时，先展示金明校区的像素风全景。

全景应当能看到校园整体轮廓、代表性建筑、水系及体育场。

随后通过镜头推进、淡入淡出或其他自然方式，进入玩家初始探索区域。

玩家可以通过地图按钮或 M 键重新查看校园全景。

探索地图划分为若干相互连接的区域，例如：

- 西大门及图书馆区域
- 中心教学区域
- 建筑工程学院及周边区域
- 广场和校园水系区域
- 体育场区域

这些只是初步分区。具体边界和连接方式需要依据真实地图，在可视化原型阶段与我讨论。

角色走到区域出口时，可以自然切换到相邻区域。

玩家走近可进入的任务建筑并互动后，可以切换到独立的建筑内部或小游戏场景。

任务完成后能够返回原来的校园探索区域。

不要在第一阶段就开发所有地图与内部场景。

## 四、玩家主角

我已经上传了一张男女大学生的像素设定参考图。

游戏开始时，允许玩家选择：

- 男大学生
- 女大学生

两名角色都应是年轻、自然、可爱的大学生形象，保留参考图中背包、蓝色系外套、发型和整体风格。

主角没有战斗职业设定，定位是探索校园的河大学生。

最终需要支持四方向移动和基础行走动画。

第一阶段只需要展示男女角色的视觉效果及选择界面，不必立即制作完整动作系统。

## 五、核心 NPC：筑小智

我上传了两张相关图片：

1. 建筑工程学院吉祥物“筑小智”的原始设计海报
2. 基于该吉祥物制作的像素风角色设定图

筑小智是游戏最重要的 NPC，也是贯穿整个校园探索过程的引导角色。

### 必须保留的视觉元素

- 具有中国传统建筑飞檐造型的屋顶帽
- 红白色服装
- 可爱、活泼的少年形象
- 建筑工程学院相关标志
- 1931 腰带装饰
- 建筑图纸筒
- 体现数字建筑技术的蓝色发光建筑模型
- 带有传统建筑与现代科技相结合的视觉特点

优先以原始设计海报作为形象依据，像素版作为转化参考。

### 角色性格

**略带神秘感的校园知识守护者。**

筑小智熟悉校园历史、建筑与许多不为人知的故事，但通常不会直接告诉玩家答案，而是通过对话和线索引导玩家自己探索。

希望它：
- 聪明、友善
- 略带神秘感
- 偶尔幽默
- 不要过于幼稚
- 说话简洁自然
- 能给玩家带来探索的好奇心

### 在游戏中的职责

- 新手引导
- 发布任务
- 提供校园知识
- 提出问题
- 提供解谜提示
- 在重要剧情节点出现

可以设计不同表情，例如微笑、疑惑、思考、惊讶和神秘微笑。

不要在第一阶段就编写大量 NPC 台词，先通过一段简短的示例对话测试形象和界面。

## 六、游戏故事

目前只确定基础方向：

玩家是一名进入河南大学金明校区探索的大学生，在校园中遇到神秘的筑小智，随后逐步发现校园中隐藏的历史记忆和特殊故事。

玩家通过探索真实地标、与人物互动、完成各种任务，逐渐揭开校园中的秘密。

整体氛围希望是：

**温馨校园生活 + 轻度神秘冒险 + 校园文化探索。**

不希望采用恐怖、血腥或过于沉重的剧情。

具体故事起因、隐藏秘密、结局及主要角色关系，暂时不定稿。

请在后续剧情设计阶段提供不同方案，让我选择和修改。

## 七、任务及关卡设计

游戏采用一条主要剧情路线。

玩家在校园主地图中移动，来到任务地点后，进入专属场景完成挑战。

不同关卡应当有不同机制，不能全部是选择题。

可能的机制包括：
- NPC 对话
- 寻找隐藏物品
- 校园知识问答
- 拼图解谜
- 线索推理
- 校史事件排序
- 迷宫
- 建筑空间重构
- 简短的计时小游戏

### 特色关卡：建筑工程学院

建筑工程学院是本次游戏的重要特色地点。

希望把软件工程（数智空间）专业与建筑知识结合起来。

初步创意是“空间重构实验室”：

玩家根据建筑平面图或空间线索，调整房间、道路或建筑模块，再通过可视化路径模拟验证自己的设计。

这是候选玩法，不是最终确定的关卡方案。

请在后续关卡设计阶段给出可玩的演示，再和我共同确定。

其他地点的任务同样暂时保留调整空间。

## 八、技术实现方向

建议技术栈：

- React
- Vite
- TypeScript
- Phaser 3
- Tailwind CSS
- JSON 数据
- localStorage
- Netlify 或 Vercel 部署

希望尽量采用简单、成熟的方案。

MVP 暂时不需要：
- 用户注册与登录
- 复杂数据库
- 多人联机
- 大型 3D 引擎
- 必须依赖外部 AI 接口才能运行的功能

但请保留合理的扩展能力。

## 九、开发阶段安排

整个项目采用以下七个阶段。

**必须遵循：每次只执行我指定的阶段。**

### 阶段 1：视觉原型与游戏界面

目标：先看到游戏实际画风，不开发完整游戏。

需要交付：
- 游戏标题首页
- 男女主角选择界面
- 金明校区全景视觉初稿
- 西大门、图书馆、建筑工程学院等代表性建筑的像素表现
- 筑小智的游戏角色形象
- 一段玩家与筑小智的示例对话场景
- 可以在浏览器中预览的原型

重点让我验收：
- 像素风格是否符合预期
- 校园建筑是否具有辨识度
- 男女主角是否满意
- 筑小智是否忠于原始吉祥物设计
- 画面比例和 UI 是否舒服

第一阶段暂时不要求完整角色移动、关卡系统或游戏剧情。

完成后必须暂停，等待我确认。

### 阶段 2：校园地图与区域结构

目标：把确认过的视觉风格应用到金明校区地图。

需要交付：
- 校园全景地图
- 主要建筑位置
- 道路、水系和绿地
- 区域划分
- 连接不同区域的地图结构
- 全景地图查看界面
- 区域切换原型

重点验收校园真实性与地图观感。

完成后暂停。

### 阶段 3：角色与探索交互

目标：让游戏真正可以自由探索。

需要交付：
- 男、女主角正式像素形象
- 四方向移动动画
- WASD / 方向键控制
- 镜头跟随
- 建筑与水面碰撞
- 建筑入口交互
- 区域自然切换
- 筑小智的场景内交互

完成后提供可试玩版本。

完成后暂停。

### 阶段 4：主线剧情与 NPC 系统

目标：建立玩家探索校园的动机。

需要交付：
- 游戏开场剧情
- 筑小智正式对话系统
- 主线任务提示
- NPC 多表情对话
- 任务发布及完成状态
- 基本故事引导

正式剧情内容需要先让我确认。

完成后暂停。

### 阶段 5：独立关卡与特色玩法

目标：制作真正有趣的闯关体验。

需要交付：
- 可进入的任务场景
- 至少两个不同机制的完整关卡
- 建筑工程学院特色玩法
- 任务完成奖励
- 从任务场景返回主地图的流程

其余关卡根据时间决定是否继续扩展。

关卡的具体设计必须与我逐步确认。

完成后暂停。

### 阶段 6：游戏主线闭环

目标：形成可以从开始玩到结局的游戏。

需要交付：
- 主线进度
- 任务完成状态
- 收集系统
- 校园知识图鉴
- 基础存档
- 最终结局
- 完整通关流程

完成后暂停。

### 阶段 7：美术完善、测试与部署

目标：交付黑客松可展示版本。

需要交付：
- 美术细节优化
- 动画和转场
- 音效及背景音乐
- 操作体验优化
- Bug 修复
- 完整试玩测试
- 浏览器兼容性检查
- 正式部署
- 项目源代码与运行说明
- 适合五分钟路演的演示版本

如果我对某一阶段不满意，请先修改当前阶段。

**未经我的明确确认，不得自动进入下一阶段。**

即使我提出修改要求，也只修改与该要求有关的部分，不要擅自重构整个项目。

开发过程中请尽量维持可运行的版本。

## 十一、重要开发原则

1. 地图、主角和筑小智必须优先参考我上传的图片。
2. 不要未经确认擅自修改已确定的美术风格。
3. 不要把尚未确定的剧情和玩法当作已经定稿的内容。
4. 重要设计决策先给我看可视化效果。
5. 不要为了增加功能牺牲游戏稳定性。
6. 实际无法完成的功能要明确说明。
7. 缺失图片时可以暂用占位素材，但不能假装是正式素材。
8. 制作实际游戏精灵表时，应检查透明背景、帧尺寸、方向、对齐和动画连续性。
9. 保留项目源代码和阶段版本记录。
10. 遵守黑客松比赛的开发时间及成果真实性要求。
